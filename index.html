O modelo em um desenho

Duas branches vivem para sempre (main e develop). As outras nascem, cumprem um papel e morrem. O caminho de uma ideia até a produção passa, obrigatoriamente, por todas elas.

main — o que está publicado develop — integração contínua do time feature/* — uma tarefa release/* — estabilização e versão

Quem sai de onde, quem volta para onde

Essa tabela é a regra do jogo neste repositório. Errar o alvo do Pull Request é o engano mais comum de quem está começando com Gitflow.

BranchNasce deVolta paraServe para
main——Sempre reflete o que está publicado. Cada commit aqui tem uma tag.
developmain—Onde o trabalho do time se acumula até formar a próxima versão.
feature/*developdevelopUma tarefa. Nunca fala com a main diretamente.
release/*developmain e developCongelar escopo, ajustar versão e changelog, corrigir os últimos detalhes.
hotfix/*mainmain e developEmergência em produção, sem esperar o próximo release.

O ciclo de release

Compare mentalmente com o repositório trunk-based: lá, publicar é git push. Aqui são seis passos — e é exatamente esse custo que você precisa sentir para decidir quando ele vale a pena.

  1. 1. Congelar

    Cria-se release/1.1.0 a partir de develop. A partir daqui, nenhuma feature nova entra nessa versão.

  2. 2. Preparar

    VERSION e CHANGELOG.md são atualizados na branch de release.

  3. 3. Estabilizar

    Só correções entram. Cada uma é levada de volta para develop também.

  4. 4. Publicar

    Merge em main → a Action de deploy leva a versão para o ar.

  5. 5. Marcar

    Uma tag v1.1.0 e um GitHub Release são criados automaticamente a partir do CHANGELOG.

  6. 6. Voltar

    Back-merge de main para develop, para que a correção não se perca na próxima versão.

Como contribuir

1

Saia da develop

git clone https://github.com/minicurso-gitflow-trunkbased/gitflow.git
cd gitflow
git switch develop
git pull
git switch -c feature/seu-usuario
2

Trabalhe e valide

cp data/participantes/_exemplo.json \
   data/participantes/seu-usuario.json
node scripts/validar.mjs
python3 -m http.server 8000
3

PR para a develop

git add data/participantes/seu-usuario.json
git commit -m "feat: adiciona participante seu-usuario"
git push -u origin feature/seu-usuario
# abra o PR com base em develop (nunca em main)

Seu commit só aparece no site quando a próxima versão for publicada — e isso é uma característica do modelo, não um defeito. Detalhes no CONTRIBUTING.md.
