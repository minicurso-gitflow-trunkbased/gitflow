Gitflow em cinco regras

O suficiente para trabalhar neste repositório sem errar o alvo do Pull Request.

  1. 1. Duas branches são permanentes

    main é o que está publicado; develop é o que será publicado. Todo o resto é temporário e deve ser apagado depois do merge.

  2. 2. Você nunca commita direto na main nem na develop

    Sempre a partir de uma feature/*, com Pull Request. As duas branches permanentes são protegidas — o push direto é recusado pelo GitHub.

  3. 3. O alvo do PR depende de onde a branch nasceu

    feature/* → develop. release/* e hotfix/* → main, e depois de volta para a develop. A CI recusa o PR se o alvo estiver errado.

  4. 4. Versão é decisão, não consequência

    O número em VERSION só muda dentro de uma branch release/* ou hotfix/*. Sua feature nunca mexe nele — mexe no CHANGELOG.md, na seção Não lançado.

  5. 5. O que entrou na main tem que voltar para a develop

    Correções feitas em release ou hotfix precisam do back-merge, senão reaparecem como bug na versão seguinte. Aqui isso vira um PR automático.

Colinha de comandos

Começar uma feature

git switch develop
git pull
git switch -c feature/minha-tarefa
# ... trabalhe ...
git push -u origin feature/minha-tarefa
# PR com base em develop

Depois que o PR foi integrado

git switch develop
git pull
git branch -d feature/minha-tarefa
git push origin --delete feature/minha-tarefa

Preparar um release

# pelo GitHub: Actions → Abrir release
# ou manualmente:
git switch develop && git pull
git switch -c release/1.1.0
node scripts/preparar-release.mjs 1.1.0
git commit -am "chore(release): prepara a versão 1.1.0"
git push -u origin release/1.1.0

Hotfix em produção

git switch main && git pull
git switch -c hotfix/1.0.1
# corrija, e então:
node scripts/preparar-release.mjs 1.0.1
git commit -am "fix: corrige ..."
git push -u origin hotfix/1.0.1
# PR para main — e depois back-merge para develop

O que doeu?

Guarde essas percepções para a discussão final do minicurso — elas são o material da comparação com o repositório trunk-based:

  • Quanto tempo passou entre o seu commit e ele aparecer no site?
  • Quantos passos foram necessários para publicar uma mudança de uma linha?
  • Sua branch conflitou? Ela tinha quantos dias de vida?
  • Em compensação: você conseguiu dizer exatamente qual versão tem cada mudança?
  • E conseguiu voltar o site inteiro para uma versão anterior com um comando?
