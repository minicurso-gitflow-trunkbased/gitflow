Análise crítica

Vantagens e desvantagens do Gitflow

Controle e previsibilidade têm preço. Veja o que o Gitflow entrega de melhor organização, releases rastreáveis e uma produção protegida e por que o excesso de branches, cerimônias de release e integrações tardias o tornam um gargalo para times que buscam entrega contínua.

Os 6 principais pontos de dor

Durante o laboratório, você sentiu na prática o esforço extra exigido para colocar uma simples alteração no ar. Abaixo estão os problemas clássicos desse modelo.

1. Alto tempo de entrega (Lead Time)

Uma mudança pronta na feature/* não vai para o ar quando termina: ela fica retida na develop esperando a abertura e estabilização da próxima release/*.

2. Conflitos severos (Merge Hell)

Branches que duram dias ou semanas divergem silenciosamente. Quando todo o time tenta integrar na develop ou atualizar o CHANGELOG.md, os conflitos são maiores e mais complexos.

3. Burocracia no ciclo de release

Publicar exige congelar escopo, criar branch release/*, rodar scripts de versão, aprovar PR para a main, gerar tag e ainda fazer o back-merge para a develop.

4. Risco de esquecer o back-merge

Correções feitas em release/* ou hotfix/* precisam voltar obrigatoriamente para a develop. Sem automação, é comum esquecer esse passo e reintroduzir o bug na versão seguinte.

5. Sobrecarga cognitiva

Iniciantes frequentemente abrem Pull Requests mirando a branch errada (ex.: feature/* direto para a main) ou esquecem de qual base cada tipo de branch deve nascer.

6. Barreira para CI/CD real

A Integração Contínua pressupõe integrar código no tronco principal várias vezes ao dia. Com múltiplas camadas de branches permanentes, o feedback real de produção é sempre adiado.

A anatomia do atraso

Veja onde o tempo e o esforço da equipe são consumidos entre a escrita de uma linha de código e a publicação em produção:

  1. Isolamento prolongado na feature/*

    Enquanto a branch vive separada, o restante da equipe altera a base na develop sem que os conflitos apareçam imediatamente.

  2. Fila de espera na develop

    Mesmo após revisão e merge do PR, a funcionalidade fica acumulada em um ambiente intermediário, sem gerar valor para o usuário final.

  3. Congelamento de escopo na release/*

    O time precisa coordenar uma parada para preparar VERSION, fechar o CHANGELOG.md e testar um pacote grande de mudanças acumuladas.

  4. Sincronização dupla no Hotfix

    Uma emergência em produção exige criar hotfix/* a partir da main, incrementar o patch e gerenciar dois merges distintos (main e develop).

Gitflow vs. Trunk-Based na prática

Comparativo direto do custo operacional que você experimentou nos dois repositórios do minicurso:

Critério Gitflow (este repositório) Trunk-Based Development
Branches fixas 2 (main e develop) 1 (apenas main)
Caminho até produção feature/* → develop → release/* → main Commit direto ou PR curto para main
Correção de emergência Branch hotfix/* + bump de versão + merge duplo git revert ou fix rápido direto na main
Tamanho dos conflitos Grandes e tardios (branches longas) Pequenos e imediatos (integração contínua)
Deploy Em lotes (janelas de release agendadas) Contínuo (a cada mudança integrada)

Quando evitar (e quando ainda usar)

O próprio criador do Gitflow, Vincent Driessen, adicionou uma nota anos depois recomendando fluxos baseados em tronco para aplicações web modernas com entrega contínua.

Evite o Gitflow se…

  • Seu produto é uma aplicação web ou SaaS com apenas uma versão ativa em produção.
  • Sua equipe pratica Integração Contínua (CI) e Entrega Contínua (CD) diariamente.
  • O time é pequeno e a cerimônia de release consome mais tempo que o desenvolvimento.
  • Você precisa validar hipóteses e corrigir problemas em produção em poucos minutos.

O Gitflow ainda faz sentido se…

  • Você distribui software empacotado (apps mobile com revisão de loja, desktop, firmware).
  • É obrigatório manter e dar suporte a múltiplas versões antigas simultaneamente (v1.x, v2.x).
  • O projeto exige auditoria formal, janelas rígidas de homologação e aprovação manual de releases.
  • O repositório é aberto com dezenas de contribuidores sem contexto prévio do projeto.
